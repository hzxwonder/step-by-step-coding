# 代码简洁、易懂、对齐风格：每一步的编码契约

## 写之前：观察项目，而不是套用通用教程
1. 打开当前步骤相关的 2–3 个相邻文件，看它怎样命名变量、定义函数、处理错误、组织测试。
2. 只记录必要约定到当前 `plan.md` 的“代码可读性与风格约定”：例如项目使用 `snake_case` 还是 `camelCase`，现有依赖里已经有哪个工具。
3. 如果仓库本身风格不统一，优先与**当前模块附近**的代码一致，而不是擅自做全仓库格式化。

## 写的时候：小白看得懂的最小实现
- 一个函数负责一个清晰的动作；当读者要上下跳跃太多层才能理解时，应考虑去掉不必要的层级。
- 有意义的命名比缩写更重要，例如 `total_amount` 比 `ta` 清晰。
- 优先使用直白的 `if/return`；能清楚说明原因时才使用抽象、装饰器、元编程或复杂泛型。
- 注释解释“为什么这一步有特殊规则”，不重复“把 x 加一”之类显而易见的操作。
- 默认先复用项目已有的函数、错误处理方式和依赖；不要引入与当前步骤无关的新包。
- **代码简洁不代表删安全检查**：输入验证、权限、空值、资源释放、超时等需要的保护不能省。
- 减少 diff：禁止顺手重命名不相关模块、重写未来步骤的代码、做全局格式化。

## 讲给小白：具体例子胜过抽象词汇
- 先描述一个正常输入发生什么，然后讲一次出错会怎样。
- 每次只挑 1–3 处关键实现，展示读者能找到的实际路径和函数。
- 复杂术语第一次出现给一句简单中文解释，例如“回调：事情发生时被自动调用的函数”。
- 如果为保证正确性保留了复杂实现，解释具体风险，不必为了“更短”改成难维护的代码。

## 在 verification.md 必须记录的 5 项审查
1. 是否引入了当前需求不需要的功能/依赖/封装？
2. 命名和控制流是否符合相邻代码且初学者容易读？
3. 是否与项目已有的目录、异常处理、测试写法一致？
4. 是否保留必要的异常处理和边界场景？
5. 是否仅修改了本步骤允许文件？

发现问题先在当前步骤修正并**重新运行相关验证**，不能把可读性审查当成写一句“OK”的形式步骤。
