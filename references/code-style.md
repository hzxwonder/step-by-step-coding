# 用最少的必要代码完成当前步骤

## 写之前：观察项目，而不是套用通用教程
1. 阅读当前步相关调用与相邻实现，通常 2–3 个文件即可。项目缺少相似文件时使用现有证据。
2. 只记录必要约定到当前 `plan.md` 的“代码可读性与风格约定”：例如项目使用 `snake_case` 还是 `camelCase`，现有依赖里已经有哪个工具。
3. 如果仓库本身风格不统一，优先与**当前模块附近**的代码一致，而不是擅自做全仓库格式化。

## 写的时候：小白看得懂的最小实现
- 一个函数负责一个清晰的动作。当读者要上下跳跃太多层才能理解时，应考虑去掉不必要的层级。
- 有意义的命名比缩写更重要，例如 `total_amount` 比 `ta` 清晰。
- 使用项目中统一的业务名称，让主要输入、处理和输出容易追踪。代码说明先给调用入口与数据流，按需展开小段真实实现。
- 优先使用直白的 `if/return`。能清楚说明原因时才使用抽象、装饰器、元编程或复杂泛型。
- 注释解释“为什么这一步有特殊规则”，不重复“把 x 加一”之类显而易见的操作。
- 默认先复用项目已有的函数、错误处理方式和依赖。不要引入与当前步骤无关的新包。
- 在用户输入、外部文件和外部服务等系统边界验证数据。检查真实的格式、范围和业务规则。
- 保留当前步骤需要的权限检查、资源释放和防止数据丢失的处理。保护措施须对应具体边界或失败条件。
- 减少 diff：禁止顺手重命名不相关模块、重写未来步骤的代码、做全局格式化。

## 每个检查和恢复分支都要有理由

增加校验、异常捕获、默认值、兼容层或重试前，先回答：它处理哪种输入或失败？这种情况由什么事实、明确需求或可信边界支持？

| 实际情况 | 应采用的处理 |
|---|---|
| 数据在入口已经验证，内部调用保持同一约定 | 直接使用数据。无需逐层重复类型和空值检查 |
| 外部 CSV 的金额可能不是数字 | 在读取边界验证金额。说明出错行及字段 |
| 当前分支违反内部约定 | 暴露错误并修复原因。不要用零、空表或成功状态掩盖问题 |
| 已知错误发生后，当前层有明确恢复动作 | 捕获对应错误。执行约定的恢复动作 |
| 当前层负责转换错误或向用户报告 | 补充具体上下文。保留错误原因并报告失败 |
| 当前层无法恢复错误 | 沿用项目的错误传播方式。保留排错信息 |
| 外部操作可能暂时失败，需求允许重试 | 明确可重试条件与次数。涉及写入时，检查重试是否会重复写入 |
| 只是猜测将来需要多种实现或旧版本兼容 | 保留当前最小实现。出现明确需求后再扩展 |

“内部已保证”要有依据。依据可以是实际入口校验、项目约定或已确认的框架行为。仅有类型注解，不足以证明外部数据已经验证。

不要用 `except Exception: return []` 把失败变成空结果。顶层捕获若用于显示错误或释放资源，可以保留。此时仍须报告失败，并保留必要的排错信息。

默认值须符合业务含义。例如，没有记录与记录金额为零可能是不同状态。只有已确认的规则允许时，才能把它们合并。

复用项目已有的边界校验。避免在每个调用层复制同一检查。不要为单次操作添加通用框架、兼容开关或配置项。

上述规则指导当前改动。修改既有保护前，先检查它的调用者和原有用途。只在获批范围内调整有证据的冗余处理。

## 讲给小白：具体例子胜过抽象词汇
- 先描述一个正常输入发生什么，然后讲一次出错会怎样。
- 用户需要了解实现时，先挑一处关键实现，给出准确路径和必要片段。
- 复杂术语第一次出现给一句简单中文解释，例如“回调：事情发生时被自动调用的函数”。
- 如果为保证正确性保留了复杂实现，解释具体风险，不必为了“更短”改成难维护的代码。

## 在 verification.md 必须记录的 5 项审查
1. 是否引入了当前需求不需要的功能/依赖/封装？
2. 命名和控制流是否符合相邻代码且初学者容易读？
3. 是否与项目已有的目录、异常处理、测试写法一致？
4. 新增检查与恢复分支是否对应真实边界或失败？是否保留必要保护？是否存在重复检查或吞错？
5. 是否仅修改了本步骤允许文件？

发现问题先在当前步骤修正并**重新运行相关验证**，不能把可读性审查当成写一句“OK”的形式步骤。

理由记录在已有的 `plan.md` 或 `verification.md`。普通代码不必逐行加注释，也不另建审查报告。

测试选择、预期依据和真实操作按 `behavior-verification.md` 执行。新增验证只覆盖当前需求与相关回归，不借测试扩展 MVP 范围。
