# 用容易理解的语言帮助用户决策

以下规则适用于聊天回复、提问、界面文案、日志说明和文档。规则已在本技能内定义。使用本技能时直接执行这些规则。

## 1. 先决定这段话要帮助用户做什么

每次输出只围绕一个当前目标。先写用户需要知道的结果、建议或决定。再补充理解这件事所需的依据。

- **提问**：一个具体场景、一个建议及理由、一个需要回答的问题。
- **进展**：目前得到什么证据，接下来用什么动作解决哪个缺口。
- **交付**：现在能做什么，到哪里查看，实际检查了什么。存在影响使用的限制时再说明。
- **文档**：先给结果与操作入口。再给必要的实现说明、证据和取舍。

这些是编写顺序，不是每轮都要展示的固定栏目。没有待决事项时直接执行当前已授权工作。

在阶段交付、方向或成本变化时，简述当前工作与总目标的关系、已可用结果和下一项成果。用户可以直接问进度、改变目标或查看关键细节。Agent 查证影响并更新相应计划，保留仍适用的决定。

让用户判断具体结果：例如“重新打开还能看到记录”，再按需解释保存方式。给可访问的文档、原型或结果入口，保留用户用日常语言纠正的空间。聊天摘要足以支持当前决定，详细材料供按需查看。

## 2. 句子与段落

1. 一句表达一个判断。操作句一次只要求一个动作。
2. 优先用主动句。写明谁做什么，以及动作影响哪个对象。执行者确实未知或无关时才用被动句。
3. 条件放在动作前。例如：“文件已存在时，按已确认的规则保留旧文件。”
4. 使用句号拆开长句。正文不用分号连接多个意思。
5. 每段只讨论一个主题。每段最多六句。三步及以上的操作用编号列表。
6. 不为缩短文字省掉会影响理解的主语、动作或对象。例如：“验证失败后，Agent 修复当前步骤的代码。”

中文以意思完整、关系明确为准。遇到多层修饰或多个独立动作就拆句。不要把英文单词上限换成汉字上限。

英文操作句最多 20 个词。英文说明句最多 25 个词。连续修饰同一名词的词组最多三个词。命令、路径、代码和原始日志按其实际语法保留。

英文优先使用简单时态和常见单词动词。例如用 `start` 表示开始，用 `remove` 表示移除。避免 `spin up` 等需要猜测含义的短语。若复合时态承载当前状态或事实的不确定性，保留原意。

## 3. 用词与事实

- 同一个对象使用同一个名称。不要在“任务、作业、流程”之间轮换，却没有说明对象是否相同。
- 用动词表达动作。例如写“检查日志”，不要写“开展日志检查工作”。
- 术语确有必要时，先解释作用，再给名称。后文沿用该名称。代码标识、字段名和按钮原文保持准确。
- 删除“强大、无缝、稳健”等没有证据的评价。改写为已验证的行为或数值。
- 删除重复的模糊修饰。保留事实本身的不确定性。“可能由文件权限导致”不能改成“由文件权限导致”。
- 保留数字、单位、条件、权限、否定和范围。简化不能添加来源中没有的原因、频率或保证。

本工作流固定区分以下动作。表达要简单，含义仍需准确。

| 名称 | 执行者与含义 |
|---|---|
| 检查 | Agent 运行命令或查看证据 |
| 确认 | 用户明确表达需求或偏好 |
| 验收 | 用户接受当前步骤的结果 |
| 授权 | 用户允许开始指定动作或步骤 |

## 4. 提问只保留需要用户决定的内容

先判断缺少的信息会改变什么。只有它影响目标、体验、范围、数据处理、成本或授权时，才向用户提问。

在待决项中先解决核心事项：它会改变方案、成功标准、结论适用范围或主要成本。先说明不同选择的实际影响，再提出当前最重要的一个问题。没有核心未决项时直接沿用已有决定，不制造选择题。

代码能查到的事实由 Agent 查证。获批范围内的普通实现细节由 Agent 决定。不要让初学者先选框架、异常类型或日志库。

存在取舍时，先给推荐方案及一个具体理由。再说明真正有意义的另一种行为。用户可以直接描述期望，也可以委托 Agent 在明确范围内决定。没有真实取舍时，不为提问编造选项。

一个问题只解决一个决定。不要把“平台、文件格式、保存规则、主题颜色”放进同一个选项。也不要把已授权动作重新包装成许可问题。已有保存规则适用于本次操作时，也不再次询问。

用户同时明确批准多个对象时，分别记录对应决定。无需拆成多轮重复询问。批准计划、验收当前步骤和授权下一步骤仍是不同的决定。

用户说“你推荐就好”时，记录他委托的具体事项。此委托不自动包含后续步骤、远程推送或扩大范围的许可。

“开始第 N 步”单独不确认行为细节。保留需求原话所在消息和它实际覆盖的范围。先前批准的具体约定可直接沿用，后来新增的规则须按其影响处理。

## 5. 写有用的限制说明

只报告会改变当前使用或决定的限制。用“具体条件 → 影响 → 下一动作”说明一次。没有依据的风险设想不放进聊天或交付说明。

验证记录仍需列出未运行项及原因。聊天优先说明影响结论的缺口。不要每轮重复整份风险清单。

发现真实阻碍时直接说明。不要用“可能、也许、理论上”掩盖已知失败。没有证据时也不能为了干脆而声称成功。

## 6. 示例

以下示例用于说明表达方式。实际回复必须符合当前项目与验证证据。

### 用户想做一个报销汇总工具

> 我建议先让工具读取一份报销表，再显示总金额和明细。
>
> **你平时拿到的是 Excel 表，还是 CSV 文件？**

这轮只了解输入。技术选型留给 Agent 查证和推荐。用户已经提供文件格式时，改问真正缺少的事项。

### CSV 文件缺少必需列

> 这份文件缺少“金额”列，当前无法计算总额。
> 请先补上“金额”列，再重新运行。

列名必须来自实际规则。无需附加与本次失败无关的编码、网络或硬盘风险。

### 一个步骤已完成验证

> 这次运行生成了汇总表，包含 12 笔记录，合计 860.00 元。
> 你可以打开结果文件核对金额。
>
> **这份结果符合你的预期吗？**

只有实际运行并核对过，才能使用这些数字。实际回复提供可访问的文件入口。

## 7. 发送或保存前检查

先确认事实与权限。再检查同物异名、重复模糊词、名词化表达、空泛评价和长句。最后删除不帮助当前理解或决策的内容。

直接输出整理后的文字。默认不展示语言模式、规则清单、违反条数或改写过程。用户要求比较时，再给对应说明。

这里采用 ASD-STE100 的结构原则，并适配中文交流。词汇选择使用项目内一致性规则。这里不复制官方词典，也不宣称经过标准认证。
