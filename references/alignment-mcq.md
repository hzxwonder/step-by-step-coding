# 记录约定并处理待定项

此文件供 Agent 维护内部记录。用户只需用日常语言表达期望，不需要回答字母或操作状态脚本。

## 默认直接记录约定

`preacceptance.md` 记录关键行为与真实证据，不是知识考试或必答问卷。每项从 Q1 连续编号，数量按实际需要。详细标准引用步骤计划，不抄成多份。

先识别核心未决项。判断依据是不同选择是否改变目标、方案、有效性结论、适用范围或主要成本。只影响呈现的偏好随后处理。已确认项直接沿用，只向用户询问最影响当前方案的一项。

```markdown
### Q1 缺失金额的处理
- **决策层级**：核心
- **选择影响**：填零或保留为空会改变汇总金额及异常记录的解释。
- **当前约定**：金额缺失时保留为空，并提示检查原记录。
- **证据**：步骤计划的金额规则，以及本次实际 prompt、日志和结果中的对应记录。
- **分歧处理**：规则变化影响 prompt、金额解析与相关 case，需要重验。
```

已有明确要求或委托且实测一致时，引用原话直接登记：

```text
answer-precheck --id Q1 --user-answer '<真实原话>' --source-kind requirement --source-ref '<原话所在消息>' --scope '<覆盖的行为与条件>' --summary '<核对结论>' --evidence '<实际证据>'
```

命令由 Agent 执行。语义判断由 Agent 负责，脚本只检查记录和状态。没有反对、“我懂了”或含混回答不能当作同意。不要为完成内部登记重新询问已经明确的决定。

## 确认的来源与范围

| 类型 | 可以确认什么 | 必须保留的来源 |
|---|---|---|
| `requirement` | 用户明确要求或接受的具体行为 | 原话、所在消息，以及当时展示的对象或问题 |
| `delegation` | 用户明确交给 Agent 决定的事项 | 委托原话、位置及边界，说明哪些条件不在委托内 |
| `approved-plan` | 用户已批准的具体约定 | 批准原话所在消息及对应计划版本、段落 |
| `discussion` | 用户提问或仍有疑问 | 记录问题所在消息及待澄清范围，只保留待讨论状态 |
| `authorization` | 仅允许开始指定动作 | 只记为授权，不记为需求确认 |
| `agent-choice` | Agent 提议或自行选择的做法 | 作为提案或普通实现记录，不自报为用户确认 |

普通实现可在授权内由 Agent 完成，但不能因此声称用户确认了具体做法。涉及核心取舍时，先说明影响，取得确认或明确委托。

例如，“开始第 3 步”单独只能用于授权。“缺失金额保留为空，开始第 3 步”则包含两个决定。可用同一句原话分别记录需求和授权，范围仅限该金额规则及对应步骤。

批准路线只覆盖已展示的约定。新增的默认值、阈值和结论条件不能附着到旧批准上。“可以”须引用当时明确的问题，不能脱离上下文解释为整步验收。

一条约定包含多个独立核心决定时，应拆开记录，或说明同一原话怎样明确覆盖它们。只确认其中一部分，不能把整组标为已确认。拆开记录不等于逐条重问，已有有效原话仍可沿用。

缺少来源字段的旧记录不能直接作为完整确认沿用。用 `reset-precheck`、`start-precheck` 整理后，引用已有的有效原话补齐来源和范围即可。不要为了升级内部记录重新向用户提问，也不要为补齐字段编造原话。

## 需要选择时才使用选项

有真实取舍时，先说明现状、推荐及原因，一次只问一个决定。用户可以直接描述期望。示例：

> 再次运行时，旧结果可以被替换，也可以保留为另一份文件。
> 我建议保留旧结果，方便比较。
>
> **你希望保留旧结果吗？**

内部可以沿用以下选项格式。它与直接约定不能混写在同一条目中。

```markdown
### Q1 重跑后的保存方式
- **决策层级**：体验
- **选择影响**：改变历史结果的查找方式，不改变已保留原始数据的计算结果。
- A. 保留每次运行的结果。
- B. 只保留最新结果。
- D. 其他想法或需要讨论。
- **当前约定选项**：A
- **证据**：计划中的保存规则，以及本次重跑结果。
- **分歧处理**：调整保存规则并重跑相关 case。
```

这类条目使用 `answer-precheck --choice ...`。仅映射用户明确表达的意思，保留真实原话。未提供的选项不能使用。

## 分歧与修订

- **仍有疑问**：直接约定可使用 `--needs-discussion`，选择项可使用 D。先解释差别，不记录为已对齐。
- **明确保留当前行为**：用 `resume-precheck --user-quote ...` 记录本次原话。
- **需要修改行为**：按相应授权修订，并用 `revise --affected Qn` 标记受影响项。验证后更新证据，未变化的确认保留。
- **只整理内部条目**：使用 `reset-precheck` 重新锁定。引用已有的对应要求或澄清原话，不为整理记录另问一次许可。涉及新行为时仍须先取得确认。
- **只补充讲解**：直接更新 `explain.md`，不重跑已完成验证，也不撤销确认。讲解暴露实质错误时转入修订。

`start-precheck` 锁定约定、计划、验证与获批文件。关键 prompt、配置或运行证据若会影响判断，应列入当前步文件范围。此后改变这些内容，需要重新核对证据，不能沿用旧运行结论。

## 记录验收

先展示一条当前版本真实 case，解释输入、适用的 prompt/配置、关键日志、输出和判定依据。用实际片段帮助用户看清结论的条件，而不只是给出 PASS 表和文档入口。同版本已展示的内容直接引用，无需重跑。

展示后用以下命令登记。`--evidence` 是项目内实际运行证据文件，`--presentation-ref` 是已向用户展示该 case 的消息或产物位置。

```text
present-case --case-id '<本次 case>' --kind real --evidence '<实际证据文件>' --presentation-ref '<已展示的位置>' --summary '<输入到输出的链路及结论条件>'
```

这一步记录 Agent 已完成的展示，不要求用户多回复一次。模拟或未运行状态不能登记为真实 case。修改实现或关键证据后，重新核对并展示受影响的 case，保留未变化的需求确认。

必要约定有真实确认与证据，且已展示真实 case 后，用户明确接受当前结果即可验收。若同一句话明确覆盖整份结果与各项约定，可分别登记到对应条目和 `accept`，无需分轮提问。

只接受一条细节不能扩大为整步验收。接受当前步也不自动授权下一步。用户同时明确表示接受当前步并开始下一步时，按顺序登记两个决定。

脚本检查来源类型和完整字段、case 展示记录与文件指纹。原话是否覆盖行为、选择是否属于核心、记录是否来自真实运行，仍须由 Agent 根据上下文和运行证据判断。填写字段不能代替这些判断。
