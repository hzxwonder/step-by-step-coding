# 预验收：用选择题确认「用户想要的行为」与「实际实现」一致

## 与知识考试的区别

| 不应该做（知识考试） | 应该做（项目对齐） |
|---|---|
| “哪个函数负责校验数据？” | “保存时遇到空金额，你希望发生什么？” |
| “为什么使用某设计模式？” | “新增记录后，你希望页面立即显示，还是手动刷新？” |
| “正确答案是 A，你选 B 所以不通过” | “你更偏向 B，但现在实现是 A。我们需要先决定是否改需求。” |
| 用户不记得术语，视为没学会 | 给出已实现行为、例子及源码，允许用户重新确认 |

每一道题都不是“考你记不记得”，而是核对一个可观察的功能约定。用户**可以改变想法**，只要明确变更，Agent 就要暂停验收、更新获批计划、重新实现并验证当前步骤。选了不同方案是有价值的发现，而不是失败。

## 出题模板

每一轮只发一道题，格式固定：

> **第 2/4 项 · 保存成功后页面怎样变化？**
>
> 例子：你输入一条午餐记录，点击“保存”。
>
> A. 立刻在列表中看到新记录
> B. 保存后弹窗提示，需要手动刷新列表
> C. 保存完成后自动跳到统计页
> D. 其他 / 不确定 / 我想讨论
>
> **你更希望哪一种？回复 A/B/C/D 即可。**

Agent 内部记录（**不要作为正确答案公布或暗示**）：
- 当前约定选项：A
- 依据：本步 `plan.md` 验收条件、实际 UI 行为、对应测试
- B/C：真实可选的不同产品决策，不要编造荒谬“错项”
- D：明确沟通出口

## 不同选择应如何处理

- **选择与当前约定一致**：用一句话确认“你希望 A，目前本步已实现并有这些证据……”，记录为「已对齐」，继续下一题。若用户同时提出保留意见，仍进入「需要讨论」。
- **选择不同选项**：不说“答错”。告诉用户“你希望 B，目前计划和代码是 A，两者不同”。简明解释体验、实现影响，然后**一次只问一个决定性问题**。暂停下一题，直到用户明确选择保留 A 或批准改成 B。
- **选择 D 或说不知道**：先用一个日常例子解释选项含义，指出目前已实现行为和证据。问用户需要哪种行为；不要强迫猜。
- **用户选择保留现状**：使用 `resume-precheck --user-quote '...'`，记录用户此次明确表述；只有期望仍不清楚时才追问，不替用户作决定。
- **用户希望修改当前步骤**：`revise --user-quote '...' --affected Q3`，更新获批的本步 plan、受影响代码、测试和 explain；验证后刷新题库，保留未变化的确认。已有明确行为要求在实现验证后可凭原话记录对齐，不再重复提问。
- **用户发现题目含混**：解释并在同意后 `reset-precheck`，纠正题目再问；不得静默改答案。

## 题目覆盖建议

4 个必覆盖维度：
1. **范围**：这一步包含/不包含哪些具体功能？
2. **正常行为**：用户的操作得到什么界面或输出？
3. **关键规则**：数据保存、状态变化、权限或重要边界采取什么规则？
4. **异常处理**：失败、无效输入、不可用服务时怎样告知与处理？

复杂步骤可加第 5–6 题确认平台兼容、交互细节、隐私/数据保留等**本步骤已实际涉及**的内容；不为了凑数引入无关知识。

## 输出原则

- 用简体中文、一句话的场景 + 一句简短问题；选项原则上不超过一行。
- 每轮只发布一题，不做分数、排名、及格线，不显示“正确答案”。
- 全部确认后生成：**本步骤对齐清单**：需求期望、真实实现位置、验证结果、仍存在的限制。
- 问题作为产品讨论，不是用户的智力/知识评估。
