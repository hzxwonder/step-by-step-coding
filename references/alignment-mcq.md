# 用具体行为确认需求

## 交流目标

帮助用户理解系统目前怎样工作，并表达自己希望的做法。先说明真实现状，再询问仍需决定的内容。
用户无需解释术语，也无需回答字母。技术建议可以说明理由，需求偏好由用户决定。

## 内部记录与对外提问

- 内部记录 1–6 项必要约定，不为题数凑问题。按本步实际内容检查范围、正常操作、重要规则和出错表现。
- 已有明确原话且当前实现已验证的项目，直接按原话记录。只把尚未明确、发生变化或仍有疑问的项目问给用户。
- 对外一次一个场景和一个问题。优先两个有意义的选项，需要时补第三个；用加粗突出核心区别。
- 末尾允许“也可以直接说你的想法，或者让我先举个例子”。无需把讨论出口编号为 D 展示给用户。
- 内部文件使用 A/B/可选 C 与 D。D 表示其他想法、不确定或需要讲解；当前约定只能对应一个实际行为。
- 一个决定过于复杂时先解释相关概念。不能把多个决定塞进一个长选项。

## 对外示例

> 目前保存时会替换旧内容。假设你昨天保存过，今天又保存了一次：
>
> A．**只留最新一份**：平时只看当前结果。
> B．**旧记录也保留**：以后可以比较前后变化。
>
> **你更希望哪种？** 也可以直接告诉我其他想法。

这里的现状必须来自实际实现。不要隐瞒现状来考用户，也不要把现状包装成必须接受的答案。

## Agent 怎样记录自然回答

| 用户表达 | 内部处理 |
|---|---|
| “只留最新的就好” | 语义明确时映射到 A，保留原话。 |
| “旧的也要” | 映射到 B；如果实现不同，先处理当前步修改并验证。 |
| “这样会占多少空间？” | 先回答问题，仍有疑问时记录 D 或 `--needs-discussion`，不当作同意。 |
| “我不知道，先举个例子” | 解释场景，再询问缺少的决定，不替用户选。 |
| 对当前唯一决定回答“可以” | 结合上一轮明确的问题，仅确认这一件事。 |

使用 `answer-precheck --id Qn --choice ... --user-answer ... --summary ... --evidence ...` 记录真实选择。
语义判断由 Agent 负责，脚本不会判断自然语言。不能凭没有反对、提到某个字母或说“我懂了”就认定同意。
用户无需知道这些字段；不把脚本输出直接展示为对话。

## 调整与沿用

- 当前约定与期望一致且无保留意见：记录 `aligned`，用一句自然的话确认理解。
- 用户期望不同：先说明体验差异与影响。用户明确要求修改后执行 `revise --affected Qn`，只更新受影响实现、验证和讲解。
- 用户讨论后明确保留现状：`resume-precheck --user-quote '...'`，记录此次原话，不重问同一件事。
- 题目有歧义：按用户澄清使用 `reset-precheck` 调整记录；锁题后不能静默改变约定。
- 实现验证后，已有明确要求可以直接记录对齐。未变化的确认保留。

## 当前步骤何时完成

必要约定都有真实用户确认和实现证据后，用几句话说明效果、验证和主要限制。
问“这一步和你希望的一样吗，还是有哪里需要调整？”。用户明确认可即可记录当前步验收。
不要求固定口令，不以知识记忆作为通过条件。下一步仍需单独明确授权。
