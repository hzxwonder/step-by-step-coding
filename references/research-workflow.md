# 用最小实验推进研究判断

用于科研代码实现、复现、评测和结果分析。先从已有协议与代码接续，当前步骤只解决一项会影响研究方向或证据可信度的问题。研究设计与实现记录共享名称或实验编号，不重复维护确认状态。

## 1. 先说清当前问题和已知事实

- 研究问题：想解释或改善什么现象，当前最关键的不确定点是什么。
- 当前假说：哪一种机制或变化可能解释现象，为什么值得验证。
- 已有证据：具体实验、数据和结果入口，适用条件与已知局限。
- 尚待验证：Agent 的建议、直觉或文献推断，标明来源与证据强度。

用户问“你怎么知道”时，指向真实实验或来源。没有证据就写待验证，不能把推荐理由改写成已经测到的效果。若有多个问题，先说明本轮选择哪一个及其原因。

## 2. 设计能改变下一步决定的最小比较

在 `mvp-design.md` 简述方法、对照、数据与划分、指标含义、比较条件、预算和判定规则。引用已有协议中的具体段落，当前未决项逐个讨论。明确的方法或对照选择可以委托 Agent；改变机制、公平性、结论范围或主要成本的选择须有来源。

判断规则在查看本轮结果前约定。例如：方法与基线使用相同样本和指标，比较主要效果，同时检查约定的资源代价。具体阈值与容差根据问题和实际依据决定。支持、不支持和证据不足分别说明下一步选项。

优先复用可运行的代码、数据、检查点与评测入口。首步尽早得到真实比较；环境或数据准备确不可合并时，说明最短准备路径。只跑通接口的工程冒烟标明其范围。合成数据适合检查实现或受控机制时，说明它与目标真实场景的区别。

理论、数值或分析任务可以使用反例、推导检查或小规模计算形成最小证据，不强行增加训练、排行榜或产品页面。

## 3. 关键实现与公平比较

实现前对齐会改变结论的公式、算法步骤、目标函数、采样、数据清洗、提示词、模型与数据版本、推理设置、指标方向和汇总单位。普通代码组织由 Agent 决定。

对照与方法的样本、划分、预处理、评测入口及资源条件按科学设计保持可比。确有差异时说明原因与影响。文献报告值与本机复现值分别标注，不默认具有完全相同的条件。数据用途与调参规则提前约定，避免用最终测试结果反复选择设计。

重复次数与随机设置按噪声和资源需要决定，不规定统一次数。保留单次结果及汇总来源；评测单位是样本、任务还是独立运行，须说明。失败、超时和未运行项按约定纳入记录，不能只保留有利运行。

## 4. 先明确资源，再运行

说明实际硬件、显存或内存、数据规模、比较和评测次数、费用或卡时上限，以及停止条件。估计注明依据，实测与估计分开。适用时先用获授权的小运行测量耗时，再讨论扩展。

方法、基线、评测、搜索、重试都计入本轮投入。资源上限、证据已足够或明确失败条件触发时停止，交付现有证据与下一项建议。需要新规模、新方法或新增费用时讨论变化，不自动反复运行到出现正结果。

## 5. 保留能复查的最小证据

按任务保存实验标识、代码版本、启动命令、数据／模型身份与样本范围、生效配置、随机设置、硬件与实际耗时。配置和日志应能关联同一次运行。

真实 case 展示一项具体输入如何经过方法或对照，得到输出，再形成指标。保留可核对的原始预测、损失或其他结果与指标计算入口，按任务选用。聚合数字、图和表能追溯到原始运行；预期样例不写入实测结果。

运行记录沿用项目已有目录或评测工具，只补足当前决策缺失的证据。默认用简短表格、必要曲线或方法示意图解释结果。有研究交互需求时再提供 HTML 原型。

## 6. 执行、科学判断和验收分别记录

| 判断 | 应说明的内容 |
|---|---|
| 执行与证据有效性 | 代码是否按约定计算，输入与对照是否正确，记录是否完整，哪些部分未验证 |
| 科学判断 | 本次证据支持、不支持或仍无法判断什么，可能解释及其证据强度，结论适用条件 |
| 用户验收 | 用户是否接受当前实现与实验交付，是否要求调整或明确授权下一步 |

科学效果不作为单元测试必须达到的断言。测试检查实现和指标计算，实验检验假说。真实负结果可以验收；实现或评测错误先修复，环境受阻保留未验证状态。

验收前回答：“这次实际做了什么？看到了什么？能说明什么？下一步最值得验证什么，为什么？”已有认可直接登记。后续路线按证据更新，科学结论变化不自动撤销仍适用的代码行为确认。
