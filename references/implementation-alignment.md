# 用真实运行对齐关键实现

用于关键实现会改变结果、体验、成本或复现方式的步骤。先说明这个细节会影响什么，再给准确内容和一条具体输入。普通实现细节由 Agent 负责，不逐项交给用户选技术方案。

## 1. 哪些细节需要抽出来

| 对象 | 应对齐的关键内容 | 真实证据 |
|---|---|---|
| 项目使用的 prompt | 实际文本、消息角色与顺序、变量值、上下文选择和输出约束 | prompt 文件或模板位置，以及本次最终发送的消息快照 |
| 生效配置 | 影响行为的实际值、单位、默认值来源、配置覆盖关系 | 配置来源与本次解析后的实际值 |
| 一次真实运行 | 具体输入、启动方式、关键阶段、错误或重试、结束状态与产物 | 同一次运行的完整日志、实际输出和必要的中间文件 |
| 关键处理规则 | 会改变数据或结果的过滤、截断、排序、阈值或错误处理 | 一条能体现差别的输入、实际规则及运行结果 |

按任务选用这些内容。只做普通计算的步骤无需添加 prompt。没有配置覆盖关系时，无需设计配置系统。优先复用项目现有记录，不为对齐搭建通用观测平台。

## 2. 实施前展示什么

把关键细节写进当前步计划，与对应的结果标准放在一起。先展示最影响用户决定的一项。其余内容提供入口，按需展开。

- prompt 展示实际拟用文本，而非只写“使用专业提示词”。变量用具体输入演示，说明会发送哪些内容、要求返回什么。
- 配置展示拟用值及实际含义，而非只列参数名。说明哪份配置会生效，哪些值可由用户调整。
- 运行过程展示预期阶段和日志格式，注明“预期示例”。此时不能声称已经跑通。

例如，计划拟用以下 prompt 处理一条报销记录。这是预期示例：

```text
将以下报销记录整理为 JSON。
返回 person、amount_yuan、category 三个字段。
只使用记录中已有的信息。金额缺失时，返回 null。
记录：张三，交通费 25 元。
```

先解释“缺失金额保留为空”对结果的影响。只有这项规则未明确时才提问。字段名称等已确认内容直接沿用，不要求用户逐句批准整份 prompt。

## 3. 实施后核对实际使用的内容

运行真实入口，并保留以下适用证据：

1. **输入与版本**：具体 case、输入内容或准确位置、启动命令或操作、代码版本与运行时间。
2. **实际 prompt**：本次渲染后的消息文本与角色。注明变量来自哪里。若发生截断、拼接或多轮调用，保留影响结果的实际内容与顺序。
3. **生效配置**：解析后的实际值与来源。模型、生成参数、阈值、路径、开关和超时等按相关性选取。读取配置文件本身不能证明该值实际生效。
4. **完整日志**：保存本次运行从启动到结束的完整记录入口，包括可用的标准输出与错误输出。聊天仅选关键行解释。完整记录不能用手写样例或挑选的片段代替。
5. **实际结果**：最终输出及必要的中间内容，连同关键规则的核对结果。

已有日志系统时直接引用本次日志。若日志未包含某项必要观测信息，在获批范围内补充最小观测方式，并说明采集边界。未捕获的历史输出不能补写为实测。

记录要能关联同一次运行，可以使用项目已有运行 ID、目录或时间标识。不要把一次运行的 prompt、另一次运行的配置和第三次运行的结果拼成同一份证据。

凭据用已遮盖标记显示。日志或请求含私有数据时，保留可检查的本地证据，向用户展示必要且已遮盖的片段。说明遮盖或未采集的部分，不把它们称为未加工的完整记录。

## 4. 怎样帮助用户作决定

先写结果，再指出决定结果的实现细节。例如：“这条记录的金额缺失，所以结果保留为空。这来自本次 prompt 的金额规则。”随后给实际文本与结果入口。

验收前至少带用户看一条当前版本真实 case，按适用范围连起输入、关键实现、日志、输出与判定依据。应让用户看到实际内容片段，再提供完整记录位置。汇总数据和技术验证不能代替这次展示。

先检查结论条件是否仍有核心分歧。例如，结果是否允许缺失、哪些输入在适用范围内、什么指标足以认定有效。只有这些已经明确时，才优先处理仅影响展示顺序或布局的偏好。

配置来源与生效值有差异时，解释真实覆盖关系。例如：“文件中是 0.5，本次运行实际使用命令行指定的 0.7。”此例只有在实际检查确认后才能使用。

用户确认的是行为及其影响。展示关键实现不等于要求用户理解所有参数。已有明确委托的选值由 Agent 记录，无需重新提问。

同一个决定在计划、prompt、配置和界面中出现时，只维护一条约定。其他位置引用它。prompt 或配置变化后，先检查影响，再重跑相关 case。只重新确认行为确实变化的部分。

模型生成内容可能变化。按已批准的字段、含义和质量标准核对，不默认要求每次逐字相同。

## 5. 缺少真实运行条件时

缺少数据、凭据或环境时，说明具体缺口和已有证据。模拟运行可以帮助检查接口，但须标为模拟，不能代替真实 case。首次 MVP 使用真实 case 跑通核心流程。前置准备说明阻碍与首次可用步骤，后续验证增量与主流程。

把证据记录在 `verification.md`，把约定放在步骤 `plan.md`。关键源码、prompt 文件、配置和运行记录纳入当前步的精确文件范围，便于检查后续变化。
