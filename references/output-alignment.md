# 对齐可观察的过程与产物

用于研究设计、实施验证和验收。先选代表性 case：写清实际样本、方法与对照、运行入口和结束条件，串起处理过程、原始输出和指标。按需要补边界或失败 case，界面按实际交互需求选用。

样例和说明也使用简明语言。先展示当前需要决定的一个片段，再按需展开细节。检查项由 Agent 筛选并填写。用户已委托的实现细节直接记录，不把整份清单变成问卷。

## 1. 实施前怎样讨论

1. 先读取已有研究协议、代码、日志和产物，区分已验证事实、用户已确认要求与待确认内容。已有明确要求直接沿用。
2. 用最小实验表、具体样本、几行日志、方法示意图和结果字段说明设计。真实结果运行后填写；有明确交互需求时提供 HTML 原型，使用标明的示例数据。实现和实验运行遵循当前授权。
3. 清楚标注“预期示例”。未确认的内容标为“待确认”。对影响体验、结果解释或使用方式的分歧，一次只讨论一个决定。已委托 Agent 决定的细节，给出建议与理由并记录委托范围。
4. 最小实验与取舍维护在 `mvp-design.md`，步骤计划引用并补当前样例与核对标准。总计划保留 case 概览，已有研究协议直接引用，同一决定维护一份来源。

不要只写“界面友好”“日志清晰”“生成报告”。说明用户在哪里看到什么、它代表什么，以及怎样检查。也不要要求用户逐一决定全部像素、内部调试字段或无关的中间变量。

## 2. 按任务选用的细节

### 可视化界面

- **入口与布局**：从哪里打开、主要区域和信息顺序、关键操作放在哪里。涉及现有界面时沿用已确认的样式。
- **控件与文案**：实际按钮名称、输入格式和默认值、点击后的反馈。确有需要时说明尺寸、颜色、字体、图例和响应式布局。
- **状态变化**：初始/空内容、运行中、成功、失败等实际适用状态分别显示什么。进度含义、按钮可用性、错误后可做什么。
- **结果呈现**：显示哪些指标或列、顺序、单位、精度。图表的轴与图例、下载入口由 Agent 采用可读默认值；指标含义变化时才对齐。

用一张草图或一个状态片段讨论一个重点。真实验证从实际入口输入、提交并核对反馈和结果，涉及保存时重新打开检查。数据正确与界面呈现分别核对，说明原型演示、真实业务运行与未验证的范围。

### 日志与终端输出

- **读者与去向**：给用户阅读还是供程序处理，出现在终端、界面还是文件，文件放在哪里。
- **格式与含义**：给出实际行样例。说明适用的时间格式与时区、级别、case 标识、阶段、计数、耗时或错误信息等字段的含义、顺序和单位。选择文本或结构化格式须与使用目的相符。
- **出现时机与粒度**：开始、阶段结束、进度更新、成功或失败时输出什么。按阶段、每项或其他频率输出，避免把“有进度”留成空话。
- **异常与结束**：成功摘要和产物位置、失败时如何定位原因。适用时说明退出码、部分成功与完全成功的区别、日志的保留或覆盖方式。

示例中的时间、耗时和运行 ID 是变化值。验收其格式与含义，不要求和样例字面相同。顺序、字段和值域中哪些固定，应在计划里写清。

### 一个 case 的运行过程

- **复现条件**：输入样本与内容、必要参数、启动命令或操作、影响复现的环境条件。
- **阶段顺序**：输入后经历哪些用户需要知道的阶段，每阶段能看到什么反馈、数据或文件。只关注对理解和排错有用的过程，不暴露全部内部变量。
- **中间内容**：需要检查的预览、统计、检查点或中间文件是什么，何时生成、是否可打开、保留多久或何时清理。
- **结束与重跑**：怎样判断完成，出错后留下什么、从哪里重试。仅在需求涉及重跑、取消或恢复时明确相应规则。

首次最小实验跑通实际输入、方法与对照、日志和可核对结果，说明本轮判断。确有准备步骤时标明首次真实闭环，后续增量服务新的证据问题。

### 最终与中间产物

- **清单和位置**：目录树、文件名或命名规则、格式、生成时机、用途，区分最终交付和需要保留的中间文件。
- **内部内容**：表格列名与顺序、字段类型、单位、精度、缺失值。报告章节与图表。图片尺寸等按实际产物选择。给出足够判断含义的内容片段。
- **一致性**：输入条数、过程统计、日志摘要、界面指标和文件内容如何相互对应。数据量大时约定抽样与完整性检查方法。
- **研究追溯**：实验编号、样本与划分、模型／数据版本、指标计算入口、单次及汇总结果、图表来源与结论条件可对应。
- **保存规则**：重复运行后覆盖还是新建、空结果和失败时生成哪些文件、是否标明部分结果。无此需求时不额外开发归档或恢复功能。

关键 prompt、生效配置和完整真实运行记录按 `implementation-alignment.md` 展开。它们与本文件中的界面、过程和产物共用一套约定，不增加一轮独立验收。

## 3. 一份可供讨论的预期示例

以下是用于核对评测链路的固定小样例，均为预期示例，不代表真实方法效果。实际项目替换为已约定输入与实验条件。

四条标签为 `[0, 0, 1, 1]`。基线预测为 `[0, 0, 1, 1]`，候选预测为 `[0, 1, 1, 1]`。按匹配标签数除以样本数计算准确率，手工可得 1.0 和 0.75。样例用于检查计算与负结果记录，不支持推广结论。

预期过程为“读取相同样本 → 核对两组预测 → 计算指标 → 保存原始与汇总结果”。日志格式按项目采用，本例只保留必要阶段：

```text
INFO experiment=E01 stage=read samples=4
INFO experiment=E01 stage=metric name=accuracy baseline=1.0 candidate=0.75
INFO experiment=E01 stage=done finding=does-not-support output=runs/E01/
```

时间、配置与代码版本保存在同一运行记录中。示例产物：

```text
runs/E01/
├── config.json
├── predictions.json
├── metrics.json
└── run.log
```

`predictions.json` 保留标签和两组预测，`metrics.json` 记录样本数、指标、各组值和差值。数值格式与字段按实际读取方约定。真实实验中的方法、配置、数据划分与判定规则须有来源，不从示例自动推定。

讨论时先解释最影响结论的缺口。例如，实际项目尚未明确比较条件时：

> 两组需要使用可比较的样本和评测规则，才能解释指标差异。我建议这一步采用同一批样本。
> **本轮按这个比较条件执行，可以吗？**

已有明确比较条件直接引用，不重问。展示真实运行时替换示例日志，并分别说明执行是否有效、当前证据能说明什么。

## 4. 实施后怎样核对

在 `verification.md` 中沿用计划中的约定名称或编号，逐项填写：

| 计划中的约定 | 实际观察 | 真实证据位置 | 结论与差异 |
|---|---|---|---|
| 本步适用的界面、日志、过程或产物标准 | 本次运行的实际内容 | 截图、日志文件与行号、产物路径与内容位置等 | 符合 / 不符合 / 未验证，并说明原因 |

记录启动入口、输入、参数、运行版本和时间，使证据能对应到同一次运行。先展示实际状态或内容，再给证据入口。不能只贴路径、日志全量或一句“文件存在”。样例、预先写好的期望文件和源码推断均不能冒充运行证据。

适用时打开真实界面、读取生成文件，检查关键阶段及相关失败表现。自动化测试可提供部分证据，但不能证明未检查的内容。不能运行时明确标记未验证，并沿用技能的受阻处理规则。

把真实片段与预期并排解释。时间、耗时等变化值按约定的格式和范围比较。若发现差异，先判断是实现偏差还是用户希望改变约定：实现偏差在当前范围内修复。需求变化更新受影响的计划、实现和证据。只补充受影响的用户确认。

在 `explain.md` 先说明结果在哪里、内容含义和怎样复现，再连接到负责这段过程或产物的关键代码。验收依据是已确认的约定与真实结果。用户理解代码与接受体验分别记录。
