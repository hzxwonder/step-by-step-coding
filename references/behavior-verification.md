# 用行为约定连接验证与结果

用于制定当前步检查、实施、排错与验收。Agent 维护测试和证据，用户通过具体输入与可见结果判断需求。复用现有计划和记录，不增加独立审批阶段。

## 1. 一项约定贯穿全过程

关键约定使用稳定的名称或编号，例如“U01 保存后重新打开”。在步骤计划中写预期及依据，在验证记录中沿用该名称或编号，记录实际检查与证据。预验收条目的 Q 编号继续用于状态工具，其证据字段引用对应约定。

| 约定 | 具体输入与预期 | 检查与实际证据 |
|---|---|---|
| U01 保存后重新打开 | 输入金额 12、备注“午餐”。保存后重新打开，内容仍为 12 和“午餐” | 从实际页面保存并重新打开，核对保存内容与页面。记录操作及产物入口 |

上表是预期示例。项目使用时须有适用的确认或委托来源，并替换成真实运行证据。已有设计中的规则直接引用，不复制出另一份需求来源。

每项本轮关键约定都有对应检查或明确的未验证说明。不要求一条规则对应一个测试文件，也不为凑覆盖率添加场景。变化值按已约定的格式、范围或含义检查。

## 2. 按改动选择检查

| 改动 | 推荐方式 |
|---|---|
| 核心计算、业务规则、状态转换 | 先选一个已明确的行为，写最小失败测试，再实现并检查通过。按需要整理代码 |
| 已发现的缺陷 | 先复现原症状，尽可能加入回归测试，修复后验证症状消失及相关原有行为 |
| 页面布局、文案、低影响原型修改 | 实际预览与操作，检查受影响状态。无需为可直接观察的小改动新建测试框架 |
| 外部服务或完整业务链路 | 使用约定输入与真实环境验证。模拟只说明模拟范围，缺失条件记为未验证 |
| 项目已有静态检查和测试 | 运行与当前改动相关的检查。只有现有检查不足且收益明确时才补充工具 |

TDD 指先用测试明确下一项行为，再完成实现。每次只推进一个关键行为，保持 MVP 主线。已有代码按当前情况补充有效验证，无需为了顺序重新创建实现。失败测试应暴露目标行为缺失或错误；依赖缺失、语法错误和环境故障不能证明测到了业务问题。

## 3. 预期结果须有依据

预期来自用户明确约定、已批准样例、可信数据或可独立核对的计算。说明关键数值或判断的来源。不要调用同一段被测逻辑来生成预期值。

测试失败时，先定位实现、测试或环境问题，再修复有证据的偏差。改变预期行为时引用对应需求来源。用户尚未决定的新行为，先说明影响并逐项解决，不能为了让检查通过自行改写约定。

对于生成文本等存在合理变化的结果，检查约定的结构、必要信息和禁止行为。记录样本、prompt、生效配置和判断依据。需要人工判断的语义或体验说明实际检查方式，不把某一次输出固定为通用答案。

## 4. 验证保持当前范围

发现新边界时，先对照已批准的使用条件。范围内偏差沿当前授权修复，新增场景记录影响并讨论处理或延后。必要的权限、凭据和数据保护按真实风险保留。

测试会暴露差异，不会自动产生扩大范围的授权。已确认延后的能力按使用条件说明，不通过额外实现将其悄悄加入 MVP。

## 5. 真实操作与版本

产品从实际页面入口操作，核对输入、提交、反馈和结果。涉及保存时关闭或刷新后再核对。接口检查与页面操作各自说明覆盖范围，重复且重要的路径按收益自动化。

验收时分别说明哪些体验由 HTML 原型演示、哪些业务已真实跑通、哪些部分未验证。每项证据能找到对应设计、实现版本与输入。

CLI 自动记录 `mvp-design.md`、`technical-plan.md`、`prototype.html` 的内容或不存在状态。设计产物变化后，旧 case 记录须重新核对。按当前授权修订并重验受影响部分，更新必要展示记录，仍适用的用户确认直接沿用。文件检查只说明版本变化，语义影响由 Agent 查证。

## 6. 复用有价值的经验

修复后更新对应约定和必要回归检查。经实际复现、适用于项目其他位置的稳定规则，可以整理进项目已有约定；通用流程的变化另按用户要求更新技能。保持每项决定的一份来源，普通故障无需追加成全局规则。
